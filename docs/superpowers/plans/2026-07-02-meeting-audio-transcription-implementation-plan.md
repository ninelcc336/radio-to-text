# 音频转文本实现计划

## 目标

基于已确认的设计说明，完成第一版本地优先音频转文本工具的实现规划。第一版目标是打通一条稳定的本地处理主链路，使用户能够导入会后录音，获得带时间戳、按匿名说话人区分的可导出纪要。

## 范围

本计划只覆盖第一版实现，不包含以下内容：

- 实时转写
- 真实姓名识别
- 小程序或移动端
- 云同步
- 协作编辑
- 云端增强与摘要能力

## 总体实施策略

按“先通主链路，再补体验层”的顺序推进，避免过早投入摘要、搜索、云端增强等扩展能力。实现工作按 6 个阶段推进：

1. 项目骨架与运行链路
2. 音频导入与预处理
3. 本地转写
4. 说话人分离与结果对齐
5. 结果展示与导出
6. 验证、打磨与交付准备

## 阶段拆分

### 阶段 1：项目骨架与运行链路

目标：

- 搭建桌面端与本地处理引擎的基本工程结构。
- 建立 UI 层和 Python 处理层之间的调用方式。
- 跑通一个最小任务流，哪怕暂时使用假数据。

建议任务：

- 初始化桌面应用工程。
- 初始化 Python 处理服务或命令入口。
- 约定任务目录结构。
- 定义前后层之间的任务输入输出格式。
- 增加基础日志与错误返回结构。

产出物：

- 可启动的桌面应用骨架
- 可运行的 Python 处理入口
- 一份任务协议定义

验收标准：

- 用户可从桌面端触发一次本地处理任务。
- Python 层可返回任务状态给桌面端。
- 失败时能看到基础错误信息。

### 阶段 2：音频导入与预处理

目标：

- 支持导入本地会议录音。
- 将不同格式录音统一转为适合模型处理的标准格式。

建议任务：

- 支持选择或拖拽导入 `mp3`、`wav`、`m4a`。
- 读取音频元数据，如时长、采样率、声道数。
- 将原始音频复制到任务目录。
- 使用 `FFmpeg` 转换为标准化工作音频，例如单声道 `16kHz wav`。
- 为预处理结果生成状态记录。

产出物：

- 原始音频保存机制
- 标准化音频生成逻辑
- 音频元数据记录

验收标准：

- 3 种支持格式都能成功导入。
- 成功生成标准化音频文件。
- 导入失败时有清晰错误提示。

### 阶段 3：本地转写

目标：

- 接入本地 ASR 模型，生成带时间戳的转写分段。

建议任务：

- 选定第一版本地 ASR 模型。
- 封装统一转写接口，隔离底层模型差异。
- 输出结构化转写结果，包括文本和起止时间。
- 将转写结果写入任务目录。
- 为长音频任务增加进度状态回传。

产出物：

- 本地转写适配层
- 结构化转写结果文件
- 基础任务进度机制

验收标准：

- 能处理约 1 小时录音。
- 输出的每段转写都有起止时间。
- 处理失败时能区分是模型错误、音频错误还是运行错误。

### 阶段 4：说话人分离与结果对齐

目标：

- 接入本地说话人分离能力。
- 将转写结果与说话人区间合并，形成最终纪要文本。

建议任务：

- 选定第一版 diarization 模型。
- 输出匿名说话人区间，例如 `A/B/C`。
- 设计时间轴对齐逻辑。
- 处理跨区间文本分段和边界冲突。
- 生成最终结构化分人转写结果。

产出物：

- 说话人分离适配层
- 对齐逻辑模块
- 最终分人文本结果

验收标准：

- 最终结果可读，能区分主要发言轮次。
- 输出结构中每段均包含时间、说话人和文本。
- 对多人打断场景能降级输出，而不是直接失败。

### 阶段 5：结果展示与导出

目标：

- 在桌面应用中展示处理结果。
- 支持导出文本文件，满足会后回看需求。

建议任务：

- 展示任务列表和单个任务详情。
- 展示最终分人纪要。
- 展示基础任务信息，如源文件、时长、状态。
- 支持导出 `txt` 和 `md`。
- 保留 `json` 作为内部或调试输出。

产出物：

- 结果查看界面
- 导出功能
- 本地任务历史记录

验收标准：

- 用户可查看完整转写结果。
- 导出文件内容与界面展示一致。
- 已完成任务可再次打开查看。

### 阶段 6：验证、打磨与交付准备

目标：

- 用真实录音验证第一版是否达到“可用”标准。
- 补齐主链路上的稳定性问题。

建议任务：

- 准备 3 到 5 份测试录音。
- 记录不同场景下的处理时长与失败情况。
- 评估转写可读性和分人可用性。
- 优化典型错误提示。
- 补齐安装说明、模型准备说明和使用说明。

产出物：

- 测试记录
- 已知问题列表
- 第一版运行说明

验收标准：

- 主流程对目标录音集可稳定完成。
- 结果足以帮助用户回忆会议过程。
- 本地离线主链路不依赖外网。

## 关键技术决策

在进入实现前，需要尽快做出以下技术决策：

1. 桌面壳选型
- 推荐：`Electron`
- 理由：生态成熟，第一版联调成本更低

2. 本地 ASR 模型
- 需要优先验证中文长音频效果、离线可用性和资源占用

3. 说话人分离模型
- 需要优先验证多人会议场景下的稳定性

4. 任务元数据存储方式
- 第一版建议优先使用文件 + JSON
- 若后续任务量明显增大，再考虑引入 SQLite

## 优先级

第一优先级：

- 音频导入
- 音频标准化
- 本地转写
- 本地说话人分离
- 转写与分人对齐
- 查看与导出

第二优先级：

- 更好的错误提示
- 更完整的任务历史
- 更清晰的任务进度展示

第三优先级：

- 摘要
- 待办项
- 决策项
- 云端增强

## 风险与应对

风险 1：本地模型安装和运行门槛较高

应对：

- 把模型依赖与应用层解耦
- 提供明确的环境准备说明
- 保留替换模型的空间

风险 2：说话人分离效果不稳定

应对：

- 先验证真实会议样本
- 将匿名说话人输出作为第一目标，不尝试做姓名识别
- 保证即使分人不完美，文本主体仍可用

风险 3：1 小时音频处理耗时长

应对：

- 增加任务进度和处理中状态
- 先优先保证稳定完成，再优化速度

## 第一阶段完成定义

当以下条件全部满足时，可认为第一版主链路已经成立：

- 可以导入本地会议录音
- 可以完成本地音频标准化
- 可以生成带时间戳的转写结果
- 可以按匿名说话人输出最终文本
- 可以在界面中查看结果
- 可以导出 `txt` 和 `md`
- 不依赖外网完成核心流程

## 下一步建议

实现应从阶段 1 开始，先做项目骨架与任务协议，不建议直接从 UI 或摘要功能入手。第一轮开发的重点应始终放在“音频进来后，能不能稳定得到可阅读的分人文本”这件事上。

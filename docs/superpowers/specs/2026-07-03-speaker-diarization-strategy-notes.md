# 说话人分离策略备忘录

## 背景

当前项目的核心价值是“把会后录音尽快转成可回看、可导出的文本”，而不是必须在第一版就把说话人分离做到极高准确率。

在实际验证中，现有启发式分人策略已经暴露出一个明显问题：  
单人录音也可能被错误拆成多个人，这种结果会直接困扰用户，甚至比“不分人”更糟。

因此，后续说话人分离能力的设计目标，不应是“默认总要分人”，而应是：

- 优先避免误导用户
- 在有把握时提供分人结果
- 在不稳定时退回纯文本输出

## 当前实现

当前版本的说话人分离实现位于：

- [diarize.py](/E:/ai-list/radio-to-text/engine/python/radio_to_text/diarize.py)

它的工作方式是：

1. 按 ASR 分段切音频
2. 提取每段的轻量声学特征
3. 使用聚类估计说话人数
4. 为每段分配匿名标签 `A/B/C`

这个实现的优点：

- 完全本地
- 依赖相对轻
- 易于接入现有处理链路

它的缺点：

- 更像启发式聚类，不是真正的正式 diarization 模型
- 对语速、音量、语气、麦克风距离变化敏感
- 单人录音也可能被拆成多说话人
- 复杂会议场景下稳定性有限

## 已确认的问题

在任务 `20260703-011057-152ca8cd` 中，录音实际上只有一个人说话，但系统识别结果为 `3` 个说话人。

这类问题的本质不是“检测到真实多个人”，而是：

- 同一人在不同说话状态下的声学特征差异被聚类器误判为不同类别

典型诱因包括：

- 语速变化
- 情绪或强调语气变化
- 近讲、远讲切换
- 录音质量局部波动
- 模拟讨论或引用他人话术时的说话方式变化

## 产品层面的判断

当前阶段不应把“必须分人”作为默认目标。

更合理的默认策略是：

- 主结果以纯文本为主
- 分人结果作为增强能力存在
- 当分人结果不稳定时，不强行向用户强调“说话人数”

这意味着：

- 不应让用户默认看到容易误导的 `说话人 A/B/C`
- 不应把 `speaker_count` 作为高优先级展示信息
- 单人录音误拆成多人时，应优先考虑降级，而不是继续强化展示

## 已讨论过但暂不采用的重型方案

### 1. `pyannote.audio`

优点：

- 正式的本地 diarization 路线
- 准确率预期更高

放弃原因：

- 分发给最终用户时，需要 Hugging Face 账号、条款接受或 token 配置
- 不适合“打包后直接发给别人用”的桌面软件体验

结论：

- 适合内部自用
- 不适合作为当前产品默认分发路线

### 2. `WeSpeaker`

优点：

- 更适合本地分发
- 可以考虑配合本地模型目录一起打包
- 不必强依赖 Hugging Face token

当前结论：

- 是后续正式替换分人模块时的优先候选方案
- 但在“是否必须分人”这件事重新判断后，优先级下降

### 3. `NVIDIA NeMo`

优点：

- 体系完整
- 正式 diarization 能力更强

缺点：

- 依赖更重
- 分发和环境准备更复杂

当前结论：

- 适合作为重型备选
- 不适合作为现阶段优先路线

## 当前推荐策略

后续应采用“保守分人”策略，而不是“默认强分人”策略。

推荐原则：

1. 默认以纯文本输出为主
2. 分人能力作为增强功能保留
3. 当分人不稳时，应允许退回“不分人”
4. 用户体验优先级高于炫技式展示

从产品视角来说，这比“明明只有一个人却显示三个人”更可接受。

## 后续可实施方案

### 方案 A：弱化默认分人展示

目标：

- 不在主界面突出显示 `speaker_count`
- 优先展示纯文本结果
- 只在分人结果有明显价值时才展示分人标签

适合：

- 近期快速改进用户困扰

### 方案 B：增加分人模式开关

可提供：

- `纯文本`
- `自动分人`

必要时再扩展为：

- `单人`
- `双人`
- `多人`

适合：

- 需要更强可控性，但又不想马上接重型模型

### 方案 C：将当前启发式分人替换为 `WeSpeaker`

目标：

- 用正式本地 diarization 方案替换当前聚类实现
- 继续保持适合桌面软件打包分发

适合：

- 后续确实决定把分人能力做成核心卖点时

## 结论

当前阶段的正确方向不是“立刻换最重的分人模型”，而是先明确产品优先级：

- 主价值是转文字
- 分人不是第一优先级
- 错误分人比不分人更伤用户体验

因此，短期内应以“弱化默认分人展示、允许退回纯文本”为主；  
中长期如果分人能力成为明确卖点，再考虑以 `WeSpeaker` 为优先路线替换现有实现。

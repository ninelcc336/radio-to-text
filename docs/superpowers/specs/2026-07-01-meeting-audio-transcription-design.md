# 会议录音转文字设计说明

## 概述

构建一个本地优先的桌面工具，用于会后会议录音转写。工具接收会议录音文件，将语音转换为文本，按匿名标签区分不同说话人，例如 `说话人 A`、`说话人 B`，保留时间戳，并导出可阅读的会议纪要。隐私是首要要求，因此核心处理链路必须默认在本地运行，不依赖互联网。云端能力或大模型增强是可选能力，且默认关闭。

## 目标

- 将会后录音转换成可阅读文本。
- 区分不同说话人，但不识别真实姓名。
- 默认将核心处理全部保留在本地。
- 支持导出结果，便于复查和归档。
- 为后续接入本地 LLM 或云端 LLM 预留扩展空间。

## 非目标

- 会议进行中的实时转写。
- 自动识别真实参会人姓名。
- 第一版支持小程序或移动端。
- 第一版支持多用户协作或云同步。
- 提供司法取证级别的逐字准确性保证。

## 产品形态

第一版产品是一个本地桌面工具。用户导入会议录音文件，等待处理完成，查看按说话人区分后的转写结果，并导出为文本或 Markdown。

建议的运行形态：

- 桌面壳负责用户交互
- 本地 Python 处理引擎负责音频和模型执行
- 本地存储负责保存录音、中间产物和导出结果
- 可选增强层负责本地或云端总结能力

## 核心用户流程

1. 用户导入 `mp3`、`wav` 或 `m4a` 格式的音频文件。
2. 系统将音频标准化为适合模型处理的格式。
3. 本地语音识别生成带时间戳的转写分段。
4. 本地说话人分离生成匿名说话人区间。
5. 系统按时间轴对齐转写分段与说话人区间。
6. 系统输出按说话人组织、带时间戳的最终文本。
7. 用户查看并导出 `txt`、`md` 或 `json`。
8. 如果启用增强能力，系统可基于转写结果生成摘要、待办项和决策项。

## 架构

### 1. 音频导入层

职责：

- 接收本地音频文件。
- 校验支持的文件类型。
- 读取基础元数据，例如时长、声道数。
- 将源文件放入任务工作目录。

说明：

- 原始音频文件应完整保留，不做修改。
- 第一版仅需支持单次任务处理。

### 2. 音频预处理层

职责：

- 将音频转换为统一处理格式，例如单声道 `16kHz`。
- 在有价值时执行基础静音裁剪或轻量降噪。
- 生成供后续模型使用的标准化工作音频。

说明：

- 预处理应以稳定性优先，避免过度处理。
- 不应使用可能删掉有效语音内容的激进清理策略。

### 3. 转写层

职责：

- 使用本地 ASR 模型处理标准化音频。
- 输出带时间戳的文本分段。
- 保留足够结构，便于后续对齐与导出。

要求：

- 必须支持大约 1 小时的录音处理。
- 模型安装完成后必须可离线运行。
- 每段识别结果必须包含起止时间。

### 4. 说话人分离层

职责：

- 使用本地 diarization 模型处理同一段音频。
- 输出按匿名说话人标注的时间区间。
- 不推断或映射真实身份。

要求：

- 输出稳定的匿名标签，例如 `A`、`B`、`C`。
- 能覆盖常见会议场景中的多轮发言。
- 在多人重叠发言严重时应尽量平稳降级。

### 5. 对齐与后处理层

职责：

- 按时间轴合并 ASR 分段和说话人区间。
- 输出形如 `[时间戳] 说话人 X: 文本` 的最终结果。
- 仅在高置信度情况下，保守清理语气词或明显重复。

说明：

- 必须保留原始语义。
- 对低置信度内容，宁可标记不清晰，也不要激进重写。

### 6. 展示与导出层

职责：

- 在应用内展示最终转写结果。
- 导出 `txt`、`md` 和 `json`。
- 保存本地任务历史，便于回看和重新导出。

### 7. 可选增强层

职责：

- 基于转写结果生成摘要、待办项、决策项和风险点。
- 支持本地 LLM 或云端 LLM。
- 必须是显式开启的可选能力，默认关闭。

隐私规则：

- 除非用户主动开启云端增强路径，否则任何音频或文本都不得离开本机。

## 数据模型

每段导入的录音都应视为一个本地任务，拥有独立工作目录和任务元数据。

建议的任务字段：

- `task_id`
- `source_file`
- `duration`
- `language`
- `speaker_count_estimate`
- `segments`
- `full_text`
- `created_at`
- `engine_config`
- `status`

分段结构示例：

```json
{
  "start": 192.4,
  "end": 205.8,
  "speaker": "A",
  "text": "这个阶段先不要扩大范围，先做试点。"
}
```

## 文件布局

建议的本地任务目录结构：

```text
tasks/
  <task-id>/
    source/
      original.m4a
    working/
      normalized.wav
      transcript.json
      diarization.json
    output/
      transcript.txt
      transcript.md
      transcript.json
    task.json
```

这个结构便于检查中间结果，也便于后续切换模型后重跑任务。

## 输出格式

### TXT

用途：

- 便于快速阅读和复制。

格式示例：

```text
[00:03:12] 说话人 A：我们先确认一下预算范围。
[00:03:40] 说话人 B：这个季度先按试点推进。
```

### Markdown

用途：

- 更适合归档为会议纪要。
- 后续可附加摘要、待办项和决策项。

### JSON

用途：

- 作为机器可读格式，便于以后扩展搜索、编辑或接入其他系统。

## 推荐技术方向

推荐的第一版技术栈：

- 桌面壳：`Electron`
- 处理引擎：`Python`
- 音频工具：`FFmpeg`
- 语音识别：本地 ASR 模型
- 说话人分离：本地 diarization 模型
- 本地持久化：任务文件 + 轻量元数据存储

采用这种形态的原因：

- Python 更适合承载音频预处理和模型编排。
- 桌面壳足以覆盖文件导入、进度展示、结果查看和导出。
- 将模型执行与 UI 分离，后续更容易替换引擎。

`Tauri + Python` 也是可行路径，但对第一版来说，`Electron + Python` 风险更低、试错成本更小。

## 第一版范围

必须包含：

- 导入本地音频文件
- 支持 `mp3`、`wav`、`m4a`
- 本地转写
- 本地匿名说话人区分
- 时间戳
- 应用内查看转写结果
- 导出 `txt` 和 `md`
- 本地任务历史

可延期：

- 转写摘要
- 待办项提取
- 决策项提取
- 关键词搜索
- 批量处理
- 云端增强开关

第一版明确不做：

- 实时转写
- 真实姓名识别
- 小程序或移动端客户端
- 云同步
- 协作编辑

## 异常处理与质量边界

产品必须明确自身边界，避免错误预期。

容易降质的场景包括：

- 多人同时说话
- 会议室回声强，或远场拾音严重
- 中英混说且包含大量专业术语
- 高频打断、发言轮次很碎
- 录音设备质量较差

异常处理原则：

- 尽量保留原始结果。
- 对低置信度内容做标记，不凭空补全。
- 保持匿名说话人标签，不猜测身份。
- 保存中间产物，便于调试和重跑。
- 允许后续使用更大、更慢的本地模型重跑。

产品目标是实用级会议回忆与整理，不是完美复原每一个字。

## 隐私模型

默认规则：

- 所有核心处理都在本地完成。

可选规则：

- 使用云端或外部模型必须由用户显式触发。

这意味着：

- 默认处理路径不能依赖外网。
- 任务数据保留在本地，除非用户主动分享。
- 未来云端集成必须通过清晰可见的显式开关隔离。

## 验证方案

第一阶段验证应使用真实会议录音，覆盖少量但有代表性的场景。

建议测试集：

- 安静会议室录音
- 普通办公室会议录音
- 有打断和重叠发言的复杂录音

成功标准：

- 能稳定导入支持的文件类型
- 能处理约 1 小时录音且不中途崩溃
- 能输出带时间戳的分人文本
- 文本足以帮助用户回忆会议细节
- 核心链路不依赖外部网络

评估方式：

- 记录处理是否完成以及失败情况
- 检查转写可读性
- 检查主要发言轮次是否能基本区分
- 验证导出文件是否可在应用外正常使用

## 交付顺序

建议的实现顺序：

1. 音频导入与预处理
2. 本地转写
3. 本地说话人分离
4. 时间轴对齐与最终文本组装
5. 结果查看与导出
6. 可选摘要与增强能力

这个顺序优先保证核心价值链路跑通，再补高级增强能力。

## 风险

- 本地模型打包后安装体积可能偏大。
- 说话人分离质量波动可能比转写质量更明显。
- 弱性能机器处理 1 小时录音可能较慢。
- 重叠发言严重的会议可能只能部分分离说话人。

缓解方式：

- 让模型选择具备可配置性。
- 保留中间产物，便于重跑和排查。
- 将增强功能与核心转写链路解耦。

## 待定实现决策

这些是实现层面的选择，不是产品范围上的未决问题：

- 具体采用哪种本地 ASR 模型
- 具体采用哪种 diarization 模型
- 第一版元数据持久化使用 SQLite 还是纯 JSON 文件
- 第一版 UI 直接基于 Electron 还是内嵌 Web 前端框架

这些问题应在实现计划阶段确定，而不需要回到产品范围重新讨论。

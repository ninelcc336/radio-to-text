# 审核反馈收敛与片段软删除设计说明

## 概述

本次调整聚焦文本产物审核区的三个问题：

- 顶部常驻状态提示容易被误读成任务信息的一部分，信息层级不清晰。
- 片段进入修正态后，“保存 / 取消”按钮尺寸过大，和片段级操作不统一。
- 重复片段无法删除，导致用户只能保留冗余内容或用文本修正绕过。

方案是在不重构整体审核流的前提下，移除顶部常驻状态提示，只保留失败反馈；统一片段编辑态按钮为小胶囊；为所有片段补充软删除能力。

## 目标

- 去掉内容区顶部常驻状态提示容器。
- 保留失败场景的即时反馈能力。
- 将片段编辑态“保存 / 取消”改成与“确认 / 修正”同级的小胶囊按钮。
- 为所有片段提供删除入口。
- 删除动作采用软删除，默认不显示、不导出，但保留底层数据。

## 非目标

- 本次不实现已删除片段恢复入口。
- 不修改左侧任务列表交互。
- 不新增独立的片段管理页面。
- 不引入新的桌面通知依赖或第三方提示组件。
- 不做真正的数组物理删除，不改变现有片段索引体系。

## 当前问题

### 1. 顶部状态提示角色混杂

当前顶部状态提示同时承载成功、处理中、失败三类消息，但位置靠近详情区，容易被理解为任务元数据的一部分，而不是临时操作反馈。

### 2. 编辑态按钮视觉过重

片段常规态的“确认 / 修正”已经是轻量胶囊按钮，但编辑态“保存 / 取消”没有复用同一组尺寸规则，造成编辑态视觉膨胀。

### 3. 重复片段无法处理

当前审核链路只支持：

- `confirm`
- `correct`

如果某个片段是重复识别结果，用户无法直接将其从最终文本中去掉。

## 方案

### 1. 收敛顶部反馈

- 移除内容区顶部常驻状态提示容器，不再为成功和处理中状态保留固定占位。
- 失败反馈改成轻量错误提示，仅在失败场景显示。
- 成功和处理中流程依靠局部反馈承担，例如：
  - 片段确认时已有忙碌遮罩
  - 导出成功无需常驻提示
  - 失败时必须给用户明确错误信息

这会让页面层级更干净，避免把全局反馈误认成任务信息。

### 2. 统一片段编辑态按钮

- 编辑态中的“保存 / 取消”改成与“确认 / 修正”一致的小胶囊尺寸。
- 保持按钮语义分色：
  - 保存：强调色或成功色
  - 取消：次级暖色
- 控制按钮高度、内边距、字号与片段操作区一致，避免编辑态额外抢视线。

### 3. 为所有片段增加软删除

#### 交互

- 所有片段都显示“删除”按钮，不限制在重点核对片段。
- 用户点击删除后，该片段立即从当前最终文本视图中消失。
- 删除动作沿用现有片段审核保存链路，而不是新增一套独立片段删除 API。

#### 数据策略

- 删除采用软删除，不从数组中物理移除。
- 被删除片段保留原始文本、时间戳和审核记录，只增加删除标记。
- 原始结果 `raw_segments` 不受影响。
- 当前可编辑结果 `segments` 中的删除片段默认不参与：
  - 文本列表渲染
  - `plain_text`
  - `speaker_text`
  - 导出结果

#### 推荐字段语义

可以在现有审核结构上扩展，例如：

- `review_status: "deleted"`
- 保留 `review_updated_at`
- 需要时可增加 `deleted: true` 之类的辅助字段，但不强制要求双字段并存

核心要求是：删除状态必须可被前后端稳定识别，并可在未来扩展恢复能力。

## 实现边界

### 前端

涉及文件：

- `app/desktop/renderer/index.html`
- `app/desktop/renderer/renderer.js`

前端职责：

- 删除顶部常驻状态提示 DOM 与样式占位
- 新增或替换失败提示样式
- 调整编辑态按钮尺寸
- 为片段操作区增加删除按钮
- 在渲染时默认过滤软删除片段

### Python 引擎

涉及文件：

- `engine/python/radio_to_text/pipeline.py`
- `engine/python/radio_to_text/cli.py`
- 如有必要，补充 `engine/python/radio_to_text/models.py` 默认字段说明

后端职责：

- 扩展 `update_segment_review` 支持新的删除动作
- 重建 `segments`、`speaker_segments`、`plain_text`、`speaker_text` 时过滤已删除片段
- 继续导出最新结果，确保删除后的片段不出现在导出文本中

## 关键约束

- 不能直接改变片段数组索引，否则会影响播放器定位、前端当前编辑索引和审核记录稳定性。
- 删除必须是可回退设计，即便本次不暴露恢复入口。
- 失败提示必须保留，避免用户在请求失败时无感知。
- 不能把“删除”实现成“修正为空文本”，否则会污染文本语义并增加导出歧义。

## 测试与验证

至少覆盖以下场景：

- 页面顶部不再保留常驻状态提示容器。
- 失败场景仍能看到明确错误提示。
- 编辑态“保存 / 取消”尺寸明显收敛，与常规操作按钮接近。
- 任意片段都能看到删除入口。
- 删除片段后，当前文本列表中该片段消失。
- 删除片段后，导出的 `txt` / `md` / `json` 不再包含该片段的最终输出内容。
- 删除一个片段不会影响其他片段的点击播放和索引定位。
- 已删除片段不会出现在 `plain_text` 和 `speaker_text` 中。

## 风险

- 现有前端大量逻辑默认 `segments` 可直接遍历；如果过滤口径不统一，可能出现“列表消失但导出还在”的不一致。
- `speaker_segments` 当前通过同步文本逻辑重建，删除状态需要明确如何映射，避免说话人文本残留已删除内容。
- 如果失败提示从常驻条切到按需显示，需要避免错误消息一闪而过或被后续成功请求覆盖。

## 成功标准

- 页面主内容区不再出现容易误判用途的顶部常驻状态条。
- 片段编辑态视觉更轻，按钮不再显得过大。
- 用户可以直接删除重复片段，且删除后不会继续出现在最终文本和导出产物中。
- 整体审核交互仍保持现有工作流，不增加额外学习成本。

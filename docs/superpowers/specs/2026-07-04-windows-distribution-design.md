# Windows 分发设计说明

## 概述

当前项目已具备本地转写的主要功能，但桌面端仍通过 `spawn("python", ...)` 直接调用源码引擎，且任务数据默认写入仓库根目录。这种形态适合开发，不适合交付给最终用户。本设计的目标是将项目改造成可分发的 Windows 桌面应用，做到安装后可直接运行，不要求用户手工安装 Python。

首发分发范围限定为 `Windows x64`，主产物为安装包，同时保留一份 portable 版本用于内部测试或快速试发。

## 目标

- 生成可安装的 Windows 桌面应用。
- 用户机器无需预装 Python。
- 应用运行数据、任务数据、日志和模型缓存都写入用户目录。
- 保留现有开发模式，避免影响日常迭代。
- 为后续代码签名、自动更新和多平台扩展预留结构。

## 非目标

- 首发支持 macOS 或 Linux。
- 首发内置所有 ASR 模型文件。
- 首发实现自动更新。
- 重写 Python 引擎为 Node.js 或服务化架构。

## 推荐方案

推荐采用 `electron-builder + PyInstaller`。

- Electron 继续负责窗口、IPC、文件选择和安装包生成。
- Python 引擎通过 `PyInstaller` 打包为独立 `engine.exe`。
- 开发环境继续直接运行 `engine/python/main.py`。
- 生产环境改为运行安装包内置的 `engine.exe`。

选择这一方案的原因是：它与当前仓库结构最匹配，改造范围可控，能以最短路径解决“用户机器必须安装 Python”的问题。

## 运行时结构

### 开发环境

- Electron 主进程仍从源码目录读取页面文件。
- Python 引擎继续通过源码入口运行。
- 根目录下现有 `tasks/` 目录可继续作为开发期数据目录。

### 生产环境

- Electron 页面资源从打包产物中加载。
- Python 引擎从 `resources/engine/engine.exe` 启动。
- 应用数据统一写入 `app.getPath("userData")` 对应目录。

建议的用户目录布局：

```text
%APPDATA%/radio-to-text/
  tasks/
  logs/
  cache/
    models/
```

这样可以把程序文件和用户数据分开，避免安装到 `Program Files` 后出现写权限问题。

## 路径与配置策略

当前 Python 配置通过源码相对路径推导仓库根目录，生产环境下需要改为显式注入。

统一策略如下：

- Electron 启动时计算 `appDataRoot`。
- Electron 在调用 Python 引擎时通过环境变量传入：
  - `RTT_ROOT_DIR`
  - `RTT_TASKS_DIR`
  - `RTT_LOG_DIR`
  - `RTT_MODEL_CACHE_DIR`
- Python 引擎优先读取这些环境变量；只有在未提供时才回退到当前源码推导逻辑。

这样做的好处是开发态和打包态可以共用一套配置读取逻辑，不必在 Python 侧硬编码 Electron 安装路径。

## Python 引擎打包

Python 打包目标是产出一个可被 Electron 直接启动的独立可执行文件。

建议流程：

1. 增加 `PyInstaller` 构建脚本。
2. 将 `engine/python/main.py` 打成 `engine.exe`。
3. 构建产物输出到仓库内固定目录，例如 `dist-python/engine/`。
4. Electron 打包前先检查该产物是否存在，不存在则直接失败。

引擎打包时需要覆盖：

- Python 依赖打包
- `faster-whisper` 运行时依赖
- `ffmpeg` 相关依赖可用性检查
- 标准输出 JSON 协议保持不变

原则上不改变现有 Electron 与 Python 之间的请求协议，只改启动方式和运行环境。

## Electron 打包与产物

Electron 侧使用 `electron-builder` 生成两个产物：

- `NSIS` 安装包
- `portable` 可执行版本

安装包作为正式对外分发形态，portable 版本用于内部验证或临时交付。

打包时应把以下内容一起纳入：

- Electron 应用代码
- 预编译的 `engine.exe`
- 必要的静态资源

首发阶段不把 Whisper 模型直接打进安装包，避免安装包体积过大、更新成本过高。

## 模型策略

模型采用“首次运行下载到用户目录缓存”的策略。

约束如下：

- 默认模型继续使用当前配置中的 `small`。
- 模型缓存目录固定落在用户目录下。
- 首次下载时需要在界面中展示明确状态。
- 下载失败时给出可重试提示，不把任务写成完成状态。

这一策略能显著降低安装包体积，也便于后续切换模型大小或计算参数。

## 错误处理与可观测性

生产环境必须补齐比开发环境更明确的报错路径。

至少覆盖以下场景：

- `engine.exe` 不存在或无法启动
- Python 引擎非零退出
- JSON 协议解析失败
- 用户数据目录不可写
- 模型下载失败
- 音频预处理或导出失败

日志应写入用户目录下的 `logs/`，并在界面错误提示中给出日志位置，方便排查用户现场问题。

## 构建流程

建议将构建流程拆成两个显式阶段：

1. 构建 Python 引擎
2. 构建 Electron 应用

典型顺序如下：

1. 安装 Node 和 Python 依赖
2. 运行 Python 打包脚本生成 `engine.exe`
3. 运行 Electron 打包脚本生成安装包和 portable 产物
4. 用样例音频做一次安装后验证

这两步必须解耦，避免 Electron 打包阶段隐式处理 Python 编译，导致失败点不清晰。

## 验收标准

本次分发改造完成时，应满足以下标准：

- 开发环境仍可通过现有命令启动。
- 生产构建可成功生成 Windows 安装包和 portable 产物。
- 安装后的应用可在无 Python 环境的机器上启动。
- 用户可导入样例音频并完成一次完整转写。
- 任务数据、日志、模型缓存均写入用户目录。
- 模型未就绪、引擎启动失败等异常场景有明确提示。

## 风险与后续

当前主要风险有三个：

- `PyInstaller` 对 `faster-whisper` 及其依赖的打包兼容性需要实测。
- 模型首次下载会拉长第一次使用时长，需要良好提示。
- 未签名的 Windows 安装包会触发系统安全警告。

分发跑通后的下一阶段建议依次处理：

- 安装包签名
- 自动更新
- 更细的日志与诊断信息
- 多平台支持评估

# 任务信息合并运行状态设计说明

## 概述

将右侧详情区中独立的“运行状态”卡片并入“任务信息”卡片，减少重复信息和视线跳转。合并后，任务信息卡片顶部新增一个醒目的状态条，使用语义化颜色直接表达任务当前状态，下面继续展示任务基础信息。

## 目标

- 移除右侧单独的“运行状态”卡片。
- 在“任务信息”卡片顶部显示高可见性的状态条。
- 状态颜色按语义区分，提升扫描效率。
- 保持现有任务元数据展示完整，不改变数据来源和任务流程。

## 非目标

- 不修改任务状态枚举或后端任务流转逻辑。
- 不新增新的任务状态类型。
- 不调整播放器、转写列表或审核工具栏布局。
- 不改动左侧任务列表中的状态展示方式。

## 当前问题

当前右侧详情区将“任务信息”和“运行状态”拆成两个卡片：

- 任务状态在任务信息明细中已经出现一次。
- 运行状态卡片再次重复提示，信息密度偏低。
- 用户需要在两个卡片之间来回看，判断当前任务状态不够直接。
- 运行状态卡片的视觉强调有限，与任务信息区割裂。

## 方案

### 1. 布局合并

- 删除独立的“运行状态”卡片。
- 保留“任务信息”卡片作为状态与元数据的统一入口。
- 在卡片标题下方、明细信息上方插入状态条。

### 2. 状态条结构

状态条由三部分组成：

- 状态标签，例如“当前状态”
- 任务状态主文案，例如“处理中”
- 阶段辅助文案，例如“转写中”

状态条应保持单独块级视觉，不与普通字段列表混排。用户在选择任务后，首先看到状态条，再查看下面的任务名称、任务 ID、源文件等明细。

### 3. 语义颜色

状态颜色按现有任务状态枚举映射：

- `created` / `ready`：中性暖色或偏黄底色，表达待处理
- `processing`：高可见性橙色，表达进行中
- `completed`：绿色，表达完成
- `failed`：红色，表达失败

如果出现未知状态，回退到中性样式，避免界面失真。

### 4. 文案策略

- 状态主文案继续复用前端现有中文映射，避免暴露内部枚举值。
- 阶段文案继续复用现有阶段映射。
- 普通明细列表中不再重复输出“状态”这一行，避免信息重复。
- “阶段”保留在明细中，便于查看任务所处细分步骤；状态条中也可显示阶段作为辅助信息。

## 交互与降级

- 未选择任务时，“任务信息”区域继续显示空态文案，不渲染状态条。
- 任务刷新、处理启动、处理完成后，状态条跟随现有渲染逻辑更新。
- 右上方的全局提示状态仍可保留其临时反馈职责，例如“任务已刷新”“处理中”，但不再依赖单独卡片承载任务主状态。

## 实现边界

只需要修改渲染层：

- `app/desktop/renderer/index.html`
- `app/desktop/renderer/renderer.js`

如需补充样式，仅在现有页面样式中增加状态条和语义色类，不引入新依赖。

## 测试与验证

至少覆盖以下验证点：

- 未选择任务时，任务信息区空态正常。
- 选择任务后，不再显示独立“运行状态”卡片。
- `created`、`ready`、`processing`、`completed`、`failed` 五类状态均能显示对应颜色。
- 状态条显示状态主文案与阶段辅助文案。
- 原有任务基础信息仍正常显示。
- 运行 `npm run smoke` 不应因渲染结构调整而失败。

## 风险与约束

- 当前 `renderer.js` 中任务信息为字符串列表拼接，合并状态条后需要改成更结构化的 HTML 输出，修改时要避免影响现有转义逻辑。
- 全局提示状态与任务状态展示职责不同，需避免两者视觉过于相似，造成用户误解。

## 成功标准

- 用户在右侧只看一个“任务信息”卡片即可判断任务当前状态和基础信息。
- 进行中、已完成、失败三类状态能被快速区分。
- 页面整体层级更集中，没有重复状态信息。
